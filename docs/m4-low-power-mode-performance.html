What Low Power Mode costs on an M4 MacBook Air

On this fanless M4, Low Power Mode cut sustained SHA-256 throughput by 52.7% and warm Speedometer 3.1 performance by 47.4%. A second battery run measured 66.8% less whole-system power under sustained SHA load and 30.1% less energy for a fixed amount of hashing.

The result

Low Power Mode roughly halved the peak CPU-heavy performance measured on this machine. The two independent workloads agree even though one is a native cryptographic loop and the other exercises a complete browser and JavaScript application suite.

Completion-time interpretation For a fixed amount of CPU work, the measured ratios imply about 111% more time for the SHA-256 workload and 90% more time for warm browser work. That reciprocal is more useful than subtracting the scores: half the throughput means approximately twice the completion time.

Browser performance

Speedometer 3.1 runs interactive web-application workloads using common JavaScript frameworks. The official aggregate fell from 53.4 to 28.9, or 45.9%. The first iteration was cold in both modes, so I also compared the median of iterations two through five: 58.33 versus 30.68, a 47.4% loss.

This is the part most relevant to editors, dashboards, complex forms, local browser tools, and JavaScript-heavy sites. Network-bound pages will not simply become 47% slower because DNS, transfer time, server latency, and human pauses do not scale with CPU speed.

Native single-thread workload

OpenSSL's speed command runs this EVP SHA-256 loop in one process and reports multiple block sizes. I used the 8192-byte column, repeated it three times per mode, and compared medians. Normal mode was 2.113 times as fast as Low Power Mode. 

openssl speed -seconds 5 -evp sha256

Power and battery life

I ran a second, paired OpenSSL batch after removing Chrome, this time sampling the Mac's own battery current and voltage every five seconds. Each mode had a 90-second idle phase, a 60-second loaded warmup so the battery gauge could settle, and a 180-second measured SHA-256 phase. The benchmark verified lowpowermode=0 for normal and lowpowermode=1 for Low Power before doing any work.

Lower power does not automatically mean lower energy for a fixed job, because Low Power Mode also took 2.108 times as long. After accounting for that throughput difference, the Low Power run used 69.9% as much energy per byte: a measured 30.1% fixed-work energy saving.

Battery-life extrapolation

If this exact workload ran continuously from a nominal 53.8 Wh full battery, the measured averages extrapolate to about 6.1 hours in normal mode and 18.5 hours in Low Power Mode—a 3.01× runtime. This is a controlled arithmetic extrapolation, not a battery rundown test or a prediction for ordinary browsing.

What this says about the web The earlier Speedometer result proves that CPU-heavy browser work slows substantially. The new power run measures the native SHA workload, not browser energy: Chrome stayed uninstalled, and Safari automation was not enabled. Real browsing also spends power on the display, radio, video, network waits, and idle time, so its battery-life gain cannot be derived from the 3.01× continuous-load figure.

Power-mode boundary

I selected Never for normal mode and Only on Battery for Low Power Mode in System Settings. The harness checked the effective battery value before every run: 

pmset -g custom
# normal: battery lowpowermode 0
# low:    battery lowpowermode 1

No privileged pmset setter was used. This avoids an administrator prompt and keeps mode changes on Apple's supported UI path. pmset -g therm reported no thermal or performance warning for either test.

Browser isolation

Every browser run created a new temporary Chrome profile and removed it afterward. Both modes used the same exact executable and build, a 1200×900 requested window, a measured 1200×813 content viewport, disabled extensions and sync, and the benchmark's automatic five-iteration runner. The result includes Chrome's DevTools version response so a stale or silently updated browser cannot be mistaken for the intended binary.

Battery telemetry

The power batch read InstantAmperage, Voltage, AppleRawCurrentCapacity, and PowerTelemetryData from AppleSmartBattery with unprivileged ioreg. Whole-system battery power is abs(current_mA) × voltage_mV / 1,000,000. I integrated the current-and-voltage samples as the primary estimate; the raw capacity counter is preserved only as a coarse cross-check. powermetrics was not used because it requires administrator access.

The battery gauge updates in visible steps, so an exploratory pair without warmup was discarded from the comparison. The corrected pair warmed the load for 60 seconds before collecting 180 seconds of data. These are whole-machine readings at the current automatic display brightness and background activity, not CPU package power. The battery was approximately 79–77%, had 13 cycles, and reported roughly 4,684 mAh full-charge capacity during this batch.

Reproduce the benchmark

The checked-in harness does not change power settings. It stops if the effective mode differs from its argument, which makes accidental or privileged configuration changes impossible. 

git clone git@github.com:marianposaceanu/dot-files.git ~/dot-files
cd ~/dot-files

# System Settings → Battery → Low Power Mode → Never
./benchmarks/m4_low_power_benchmark.sh normal

# System Settings → Battery → Low Power Mode → Only on Battery
./benchmarks/m4_low_power_benchmark.sh low

# Power batch: run once in each already-selected mode
python3 benchmarks/m4_power_benchmark.py normal
python3 benchmarks/m4_power_benchmark.py low

What the result does not mean

  • SHA-256 is a sustained native crypto workload, not a universal single-thread score.
  • Speedometer is intentionally CPU- and browser-heavy; network-bound browsing has a smaller end-to-end penalty.
  • The comparison describes this M4 MacBook Air, macOS build, and browser build. Other Apple chips and OS versions can use different power policies.
  • Five browser iterations expose cold versus warm behavior but do not replace repeated, randomized A/B/A trials.
  • Battery telemetry has much lower time resolution than dedicated lab instrumentation; repeated randomized runs and a physical power meter would tighten the estimate.
  • The battery-life figures are arithmetic extrapolations for continuous SHA-256 load, not measured browsing runtimes.

On this M4 MacBook Air, Low Power Mode is an efficiency policy with a visible performance trade-off—not a free battery-life toggle.
